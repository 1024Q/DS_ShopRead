# 节点到期计划调度内核

本轮采用“每店到期计划 + 节点统一派发 + 安全断点分段执行”。业务采集器、登录资料、业务表与分页断点格式保持不变。

## 计划与执行

- `node_dispatch.NodeDispatch.plans` 保存每店每个实际查询范围的一条计划，不为等待计划创建协程。重复到期更新同一条需求。
- `scheduling_kernel.SchedulingKernel` 是不访问数据库或浏览器的确定性决策层。节点读取名额、活跃店铺、单店并发、同业务模块互斥在这里一次性检查和预留。
- `scheduler.Scheduler` 只发现和核验持久化计划，不再使用旧的扫描候选筛选器、冻结队列或二次 SlotDispatcher 派发。
- 主任务仅用于展示；范围、分页、失败与上传进度仍归属实际子步骤。

## 执行生命周期

`reserved → reading ↔ database / resuming → finishing → 进程内任务真正退出`

- 浏览器准备占用活跃店铺位置，不占读取名额；准备失败记录资源冷却，不伪造一次接口读取失败。
- 就绪店铺先取得实际执行位置，再准备其他休眠店铺，防止就绪店铺被后续准备不断挤出。浏览器准备耗时不计算店铺的执行轮次预算；轮次从实际执行预留开始。
- 入库阶段释放节点读取名额，但保留单店执行位置和同业务模块互斥。提交完成后，通过同一个内核重新申请续读名额。
- 完成读取后的发布与状态确认不再占读取名额；业务互斥直到执行实例退出才释放。
- 上传独立运行，中心断线不撤销本地已提交数据。写入压力过大时停止接收新读取；派发层另外设有由读取上限推导的有界积压保护，不增加配置队列。
- 完成、取消清理结束、入库和资源准备完成均立即请求派发。所有等待需求共用一个低频资源核验定时器。
- 扫描层每批登记完成后统一请求派发，禁止逐条登记时重复全量派发。批处理范围不跨数据库等待；已有执行的完成补位不被扫描阻塞。写入压力只对已到期需求探测，并且每店每轮只探测一次。
- 派发不反向唤醒扫描循环，避免“扫描 → 派发 → 扫描”的空转。
- 升级维护期禁止新的执行和浏览器准备，但允许已运行任务在入库后续读并保存最终断点，避免升级和续读互相等待。
- 升级占用检查使用内核的真实执行预留，包含最终发布阶段，不依赖可能遗留的店铺运行提示集合。

## 公平与恢复

店铺轮转优先，同店内按相对超期程度选择。现有每批秒数决定有其他到期店铺等待时的让位时机。长列表在分页断点成功保存后让位，未完成分页不标记成功。没有可执行同伴时不人为浪费名额。

取消会等待原生数据库线程和共享查询的必要清理，不提前释放业务互斥。预留使用代号核验，旧回调不能释放新实例。重启沿用现有任务账本和断点，并先核验遗留执行占位。退款等写操作不参与查询合并或重放。

## 计时与界面

等待名额、浏览器准备、页面加载、接口读取、数据库写入、等待续读和上传确认分别计时。页面加载有独立截止时间，不消耗接口读取预算；数据库和续读等待也不消耗读取预算。

后台和 Qt 控制台显示读取名额、入库、等待续读、结果确认、浏览器准备及等待原因分布。等待项给出原因开始时间和解除条件；无法确定解除时间时不显示虚假的预计时间。多节点合计只统计已经上报新字段的节点，不能当作新的全局并发限制。

读取完成后的辅助核验继续显示实际步骤；只有等待续读名额时，用资源等待原因替代旧的读取步骤。手动追加的完整读取即使暂时没有店铺名额，也保留一次性重跑标记。

诊断和执行日志只保存文件。现有频率、并发、休眠、停用状态以及业务与登录数据均沿用已有配置。

## 验证入口

- `backend/tests/test_scheduling_kernel.py`：原子预留、业务互斥、取消排空、写入后续读、店铺公平、浏览器准备、安全分段与阶段计时。
- 现有断点、共享查询、业务发布、上传与休眠测试继续作为回归门禁。
- 本机验收应比较更新前后完整配置、运行 PID / boot_id、签名文件哈希、新提交数据与中心确认；生产平台故障不得因为调度重写而被隐去。
